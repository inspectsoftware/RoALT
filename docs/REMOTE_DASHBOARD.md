# RoALT Remote Dashboard & Control — Architecture & Handoff Memory

> **Status (2026-11-24):** Phase 1 hardened after `docs/REMOTE_SECURITY_AUDIT.md` (protocol v2). The old deploy on `roalt.dev/remote/` speaks protocol v1 and must be replaced by the `remote.roalt.dev` deploy before release. Phone control works on the real app (indev 1528): tap = Windows touch → click, drawn joystick + jump hold W/A/S/D/Space, drag = right-button camera turn (`src-tauri/src/instances/remote_input.rs`); on Windows 10 previews capture with the yellow border only while a phone watches. The desktop app with Remote is not released yet.

## 1. Agreed Decisions & Constraints

- **Product fit (`PRODUCT.md`):** Opt-in (off by default), zero RoALT user accounts, zero central database, end-to-end encrypted (E2EE). `.ROBLOSECURITY` cookies, vault passwords, recovery codes, and cookie exports **never leave the PC** and are hard-excluded from the remote command allowlist.
- **Hosting:** a dedicated origin on the **Hostinger VPS**, so no other `roalt.dev` page shares the dashboard's IndexedDB keys.
  - Web dashboard SPA at the site root `https://remote.roalt.dev/` (from `web/remote/dist/`, Vite `base: "/"`), with its own strict CSP (Caddy block in `server/remote-relay/README.md`).
  - Stateless in-memory blind Rust WebSocket relay on the same VPS at `wss://remote.roalt.dev/ws/remote` (from `server/remote-relay/`). The desktop's `WEB_BASE_URL` and default relay URL point here. The QR link never names the relay: the hosted dashboard only talks to the official relay, so a custom relay needs a dashboard you run yourself (a localhost / 127.0.0.1 dev build defaults to `ws://127.0.0.1:8788/ws/remote` and honours `?relay=`).
  - Threat model and accepted residual risks: `docs/REMOTE_THREAT_MODEL.md`.
- **Multi-PC ready:** One browser dashboard stores multiple paired PCs in IndexedDB and multiplexes them over a single WebSocket per relay URL.
- **Phased rollout:**
  - **Phase 1 (Complete in workspace):** E2EE pairing (QR code + manual 8-char code with 6-digit SAS), multi-PC dashboard, real-time accounts/instances/metrics/crashes/bulk-progress sync, `IntersectionObserver`-throttled live JPEG previews (grid tiles 2 FPS / 240px, 30 FPS / 640px inspector, all paused after 2 minutes without a touch, click, key or scroll until the next one; the PC keeps at most 3 unacknowledged frames per stream), and full management controls.
  - **Phase 2 (Planned next):** Live interactive in-game control via WebRTC P2P video stream + mouse/keyboard/mobile touch input (`SendInput`), signaled over the existing Phase 1 E2EE channel (`WebRtcSignal` variants are already reserved in `protocol.rs`).
- **Windows Lock Screen constraint (`session.rs`):** While Windows is locked, monitoring/launching (if vault unlocked)/rejoining/closing/limits/panic-kill/shutdown still work, but DWM window capture and `SendInput` are blocked by Windows. RoALT reports `windowsLocked: true` and the web UI displays a clear *"Windows is locked — management only"* banner.

## 2. Cryptographic & Wire Protocol Spec (Do Not Break Compatibility)

- **Primitives:** NIST P-256 (`p256` crate in Rust ↔ native browser `SubtleCrypto` with non-extractable keys in IndexedDB), HKDF-SHA256, AES-256-GCM.
  - Public keys: 65-byte SEC1 uncompressed (`0x04 || X(32) || Y(32)`).
  - Signatures: 64-byte raw IEEE P1363 `r || s` over SHA-256.
- **pcId rule:** `pcId` = first 16 bytes of `SHA-256(pcSecretHash hex string)`; the relay refuses any other `pc_hello`, so knowing a pcId can't squat it. Shared test vector: `sha256_hex("pc-secret")` → `d5d6cc8b-7d41-ca38-749e-6786be4d1849`.
- **Per-relay secret (`PcIdentity::for_relay`):** the official relay (`wss://remote.roalt.dev/ws/remote`; the old `wss://roalt.dev/ws/remote` setting is read as it) gets `pcSecretHash = sha256_hex(pc_secret)`. Any other relay gets `pc_secret' = base64url(HKDF-SHA256(salt = "roalt-remote-v2-relay-secret", ikm = pc_secret, info = relay URL))` and so its own pcId, so a custom relay can never replay this PC's credential on the official relay.
- **Relay binary header (17 bytes):** `[version: 0x01][target_uuid: 16B][opaque_payload...]` (relay rewrites UUID between `pcId` and `viewerId`; any other version byte gets `{"t":"err","code":"bad_version"}` and the frame is dropped).
- **Protocol version:** `PROTO = 2`. `pc_hello` carries `"proto": 2, "app": "<RoALT version>"`; the viewer's `subscribe` (`{t:"subscribe", proto:2, pcs:[{pcId, deviceId, roomToken}]}`) and every `pair_join` carry `"proto": 2`. The relay's `MIN_PROTO = 2`: a missing or lower proto gets `{"t":"err","code":"upgrade_required"}` and the socket closes. The PC then shows "Update RoALT" and stops retrying until woken; the dashboard stops reconnecting and shows a reload banner.
- **Relay rules (`server/remote-relay/src/lib.rs`):**
  - Frame caps: PC binary 256 KiB, viewer binary 64 KiB, text 32 KiB. A larger frame gets `{"t":"err","code":"frame_too_large"}` and is dropped (socket kept); WebSocket frames or messages over 257 KiB end the socket. The PC never seals an encrypted frame over 240 KiB.
  - Inbound budgets: token buckets per connection (PCs 4 MiB/s, 8 MiB burst, 400 msg/s; viewers 256 KiB/s, 1 MiB burst, 200 msg/s) and per client IPv4 address or IPv6 /64 across its sockets (8 MiB/s, 1000 msg/s). Over budget the relay stops reading the socket until the budget refills (TCP slows the sender) and sends `{"t":"err","code":"rate_limited"}` at most once a second. `pc_tokens`, `pair_open` and repeated `subscribe` are limited to 4/s per socket. More than 64 binary frames in 10 s for targets the socket isn't attached to close it.
  - Outbound queues are byte budgets: 2 MiB per socket and 256 MiB globally, each message counted at its length plus 256 bytes and released when the socket's writer takes it to send (so a frame being written to a slow reader pins nothing). A routed frame reserves its socket first: a full socket frees room from its own largest other peer stream when that holds more than the pushing peer's stream, otherwise only the new frame is dropped, so busy PCs can't starve a dashboard's other PCs. It then reserves the global budget: a full relay frees room from the largest tenant holding at least what the receiver's holds, compared at the first address level where the two differ (IPv4 /24 or IPv6 /32, then the IPv4 address or IPv6 /48, /56, /64, then the sockets), so many small addresses in one prefix are weighed as that prefix and a neighbour of a prefix filling the relay takes room from it. The victim loses the oldest frames of its largest stream (relay messages such as `pc_online` stay); a socket with no queued frames is skipped, never closed; a tenant no smaller than every other sheds nobody. When one victim holds less than the frame needs, the next outranking ones shed too, up to 8; if all of them together can't cover it, nobody sheds and the frame is dropped. Address groups only rank, they have no budgets. The ranking is rebuilt at most every 5 ms relay-wide from the sockets that hold queued frames, and once more when a push finds too little to shed and a backlog has started since the last build; a push skips the entries that have nothing left to shed and sheds from at most 8. The relay's own messages use a 64 KiB allowance per socket outside the shared budgets, so no client can crowd out another's `pc_online` or `viewer_joined`. Replies a client provokes (`pong`, errors) use that allowance too, so a slow reader asking for them holds none of the shared budget. A write stalled for 10 s, or a queued message older than 15 s, closes the socket.
  - Timeouts: WS Ping every 25 s; idle close after 70 s without an inbound text or binary message (Ping/Pong don't count; the dashboard's main and pairing sockets send `{"t":"ping"}` every 25 s, so a pairing stays open while the user approves); the first registering message (`pc_hello` / `subscribe` / `pair_join`) within 10 s; a viewer attached to no PC and holding no pairing room is closed after 30 s, however many pcIds it subscribes to (a dashboard whose PCs are all offline reconnects quietly).
  - Caps: 4096 connections. Nested caps of 32 per IPv4 address or IPv6 /64 (a home's 16 PCs and its dashboards share one address), and 1/64, 1/16 and 1/4 of the relay per IPv6 /56, site (IPv4 /24 or IPv6 /48) and IPv6 /32 (64, 256, 1024 by default), all checked and charged in one step. A full address lets a newcomer close that address's socket that has been silent for over 30 s (live clients ping every 25 s), so a home gets back in after a router blip. A full group or relay lets a newcomer whose subgroup holds at least 2 fewer sockets than the largest subgroup, compared at the first level where they differ, close that subgroup's newest socket at any age; the newcomer's subgroup then closes no other socket for 10 s, the largest subgroup never trims anyone, and the closed socket frees its seat at once. Only the closing side waits, so a tenant trimming its own big subgroups can't shield them from a neighbour. Otherwise HTTP 429 (a full address or group) or 503 (a full relay). Connect-rate buckets: 10/s per address or /64, and a coarser group's bucket scaled by its cap. Every connection that passes them is charged to every level, but a coarser bucket only holds up a subgroup that has been connecting more than its share there (the group's rate over its subgroups with a socket open, measured over about a second), the subgroups the relay has not seen yet counting together as one. So neighbours that retry a lot only run out their own share, a known or new neighbour still gets in, and rotating through fresh /64s or /48s is held to the bucket of the prefix above them. Inbound byte rates are also shared per /56, site and /32 (2×, 4×, 8× the per-address rate). 16 subscriptions per viewer (each refused PC gets `{"t":"pc_err","pcId","code":"too_many"}`), 16 viewers per PC and 3 per device token (a newer socket with the same token replaces the oldest; a subscriber with a valid token for a full PC gets `{"t":"pc_err","pcId","code":"full"}` and is attached when any slot frees, a `pc_tokens` revoke included). A subscriber whose token is still refused 2 minutes after the first refusal stops waiting, also across repeated `subscribe`s, whatever token they carry. When the PC comes online or slots free up, the longest-waiting subscribers are attached first. A `subscribe` item with `"restart": true` for a PC the socket is already attached to gets `pc_online` again and the PC gets `viewer_joined` again (a fresh session, same slot).
  - `viewer_joined` carries `{viewerId, deviceId, tokenHash}`; the PC refuses a session whose `tokenHash` is not that device's room token. A viewer the PC kicked (`kick_viewer`), or one a newer socket of its device replaced, is not attached again until it subscribes with `"restart": true` or a new token (or the PC sends a new `pc_hello`); a plain `subscribe` for its other PCs only gets `pc_offline` for this one. The PC can give a reason: `{"t":"kick_viewer","viewerId","code":"paused"|"device_sessions"}` reaches the viewer as `{"t":"pc_err","pcId","code"}` (any other code as plain `pc_offline`), and a socket a newer one of its device replaced gets `pc_err` `replaced`. The dashboard then shows why: for `paused` it stops retrying until the PC comes back online, for `device_sessions` it keeps its slow retry (the PC drops a dead session after 15 s), and for `replaced` it retries once with `restart` and lets go of that PC until reloaded only if it is replaced again within 10 minutes. A kick without a reason (a quiet or broken session) is retried with `restart` within 10 s.
  - A revoked token, a wrong token and an offline PC all get `pc_offline`; there is no `pc_revoked`.
  - Optional `RELAY_MIN_APP_VERSION`: a `pc_hello` with an older `app` gets `{"t":"err","code":"upgrade_required","min":"x.y.z"}`, then close.
  - Browser sockets must carry `Origin: https://remote.roalt.dev` or `http(s)://localhost[:port]` / `http(s)://127.0.0.1[:port]` (others get HTTP 403); sockets with no Origin (the desktop app) are allowed. `X-Real-IP` is trusted only from loopback or `RELAY_TRUSTED_PROXIES`.
  - PairIds are 16–64 lowercase hex characters (`pair_err bad_pair_id` otherwise), so a typed manual code (6–12 letters and digits) can never resolve as somebody's pairId. `pair_open` claims the pairId and manual code atomically; one owned by another PC gets `{"t":"err","code":"pair_taken","pairId"}`. A `pair_join` from a second socket into a locked room still reaches the PC as `pair_joined` (so the PC can abort), while that joiner gets `pair_err busy`. When the first joiner's socket closes the PC gets `{"t":"pair_left","pairId","viewerId"}`. Pair-join rate limits count pairings: 30 per minute per IP or /64 and 60 per /48, where a rejoin of the socket's own room only takes the socket's control budget and a room's holder may join it 4 times (`pair_err busy` after). Wrong manual codes: 600 per minute relay-wide (`MANUAL_MISS_MAX`) and at most 1/16 of that per IPv4 /24 or IPv6 /32; a network over its share, and once the relay-wide budget is spent any network that guessed wrong this minute, gets `pair_err rate_limited` and a close on manual-code joins (the dashboard says to try again or scan the QR code); a network with no wrong code this minute is always let in, and QR joins are unaffected. `pair_join` and `pair_msg` `data` is at most 8 KiB (`MAX_PAIR_DATA`, `frame_too_large` otherwise); once the PC approved its joiner it sends `{"t":"pair_extend","pairId"}`, which keeps a room that has a joiner for 60 s more (`PAIR_CONFIRM`), at most until 180 s after it opened. When a room its joiner holds goes away (`pair_close`, the PC's socket closing, expiry), the joiner gets `pair_err closed`. `pair_msg` takes the PC socket's control budget. Subscribe items are parsed one by one, so a bad item is skipped.
- **Session handshake (`payload[0] = 0x01`, 130 bytes):**
  - `[0x01][ephem_pub: 65B][ecdsa_sig: 64B]`
  - Signed transcript: `"roalt-remote-v1-hs" || role_byte (0x01=PC, 0x02=Viewer) || pc_id(16B) || device_id(16B) || ephem_pub(65B)`.
  - Session keys: `HKDF-SHA256(ikm = ECDH_X(32B), salt = pc_ephem_pub(65B) || viewer_ephem_pub(65B), info = "roalt-remote-v1-session")` → 64 bytes (`k_pc_to_viewer[0..32]`, `k_viewer_to_pc[32..64]`).
- **Encrypted data frame (`payload[0] = 0x02`):**
  - `[0x02][seq: u64 BE][ciphertext || 16B GCM tag]`
  - Nonce (12B): `[dir (0x01|0x02), 0, 0, 0, seq_be(8B)]`
  - AAD (10B): `[0x01, dir, seq_be(8B)]`
  - Plaintext prefix: `0x01` = UTF-8 JSON (`RemoteCommand` / `RemoteEvent`), `0x02` = binary JPEG preview `[0x02][id_len:u8][id][seq:u32 LE][age_ms:u32 LE][status:u8][jpeg_bytes...]` (JPEG at most 200 KiB).
- **Session rules (`remote/mod.rs`, `dispatch.rs`):**
  - Key confirmation: a handshake alone (a replayed one verifies too) makes nothing happen. The dashboard sends `{reqId:0, op:"ping"}` right after its handshake; on the first frame that decrypts the PC counts the session as connected and sends the snapshot, and only confirmed sessions get broadcasts or previews. The dashboard shows the PC online only once that snapshot arrives; until then it retries at 10/20/40/80 s. With the PC's handshake in hand it resends its own handshake and `requestSnapshot`; without it, it drops its session and subscribes again with `restart: true` for that PC (it keeps its viewer slot; the PC starts a new session on the repeated `viewer_joined`); with no `pc_online` (or after `pc_offline`) it subscribes again, also with `restart: true`, so a lost `pc_online` for a PC the relay already attached it to is announced again. A session with keys that has received nothing that decrypts for 12 s (the PC sends confirmed sessions their metrics every 3 s) is treated as gone even without `pc_offline`: the dashboard drops it, shows the PC as connecting and subscribes again with `restart: true`. A `pc_online` whose session setup outlives its socket is dropped. A hidden tab closes its relay sockets after 30 s and reconnects when shown. A socket the relay closes with `no_purpose` (nothing to attach to) doesn't reset the backoff. Retries are combined into at most one `subscribe` per relay per second. A repeated `pc_online` for a PC that already has a session is ignored (relay re-announce). A verified PC handshake on an established session re-keys and counts as a strike. A handshake that fails to verify shows "may run an older RoALT, or its key changed".
  - The dashboard sends an E2EE `{reqId:0, op:"ping"}` every 5 s to each PC with an established cipher; the PC drops a session with no decrypted frame for 15 s (`kick_viewer`, that session's input released). At most 3 confirmed sessions per device. To match, one browser follows one PC from at most 3 tabs at once (Web Locks `roalt-remote/<pcId>/0..2`; no limit where `navigator.locks` is missing): a further tab says the PC is open in 3 other tabs, never subscribes, and connects as soon as one closes; a tab hidden for 30 s gives up its slot with its sockets.
  - Budgets per device (shared by its sessions and kept across them while the PC stays connected): RPCs 30 burst at 10/s with at most 4 commands running at once; snapshots 2 burst at one per 2 s (`requestSnapshot` and the first snapshot only mark one due, sent as the budget allows); input 120 burst at 240/s; lifts (key up, touch / camera `up`) have their own budget of 60 burst at 120/s, and a lift over it also releases that session's input. Refused requests get `rpcResult` code `rate_limited`. A spawned command reads the device's role again before it runs, so a revoke, pause or downgrade wins over frames already buffered; the session loop also handles control signals before relay frames. Request ids are random u32 values (never 0) chosen by the dashboard and keyed per PC (`pcId:reqId`); the PC echoes them unchanged.
  - An event that still doesn't fit a frame becomes a short error: an `rpcResult` with code `too_large`, or for a snapshot or any other event a `notice` (`error: true`) that the dashboard shows (as a banner while a snapshot is up, cleared by the next snapshot). Nothing is dropped silently.
  - The PC's frames to the relay go through a 64-message queue drained by its own task; a send stuck for 10 s ends the connection, and previews are dropped instead of waiting when the queue is full.
  - Remote-only DTOs (`protocol.rs`, `Remote*` bindings): `RemoteAccount{id, username, displayName, alias, color, main, status, groupIds}`, `RemoteGroup{id, name}`, `RemoteFavourite{id, name, placeId}`, `RemoteTarget{kind, placeId}`, `RemoteInstance` (no pid, jobId, launchData or codes), `RemoteCrash`, `RemoteBulk`. Notes, launch args, custom flags, profiles, link and access codes are never sent. Favourites launch by id: `{op:"launchFavourite", favouriteId, accountIds (empty = the favourite's own accounts), fpsCap}`; `{op:"instanceRejoin", id}` reuses the instance's own target.
  - Every list that can grow is paged at 24 KiB of item JSON (`PAGE_BYTES`): the carrying event (`snapshot`, `accountsUpdated`, `instancesUpdated`, `metricsUpdated`, `bulkProgress`) holds the first page, and the rest follows in order on the same session as `{t:"accountsPage", batch, offset, accounts}` or `{t:"page", batch, offset, page:{list: "groups"|"favourites"|"instances"|"metrics"|"crashes"|"bulkItems", items}}` (a single larger item gets its own page). Each carrying event has a `batch` number of its own that its pages repeat. The dashboard appends a page only when its `batch` is that of the event that last set the list and `offset` equals the list's current length; anything else (a page of an update whose carrying event was lost, an offset below or past the length) means a page got lost, so it shows a notice and asks for a fresh snapshot (backing off from 2 s to 60 s; a request the backoff holds back is sent when the backoff ends). A list over 10,000 items is cut there with a visible notice, and later pages of that list are ignored instead of read as lost ones. Group and favourite names, client notes, crash reasons and bulk-launch failure messages reach the dashboard clipped to 256 characters, so no single item comes near the frame cap. Every decrypted event is shape-checked (`web/remote/src/validate.ts`); an event type the dashboard doesn't know is ignored, a malformed one is dropped and flagged, and the 5th within a minute ends the session (unsubscribe until reload or re-pair), as do 50+ strikes in 10 s and a failed handshake check. A root error boundary shows a Reload button if the dashboard crashes. PC names are shown cleaned (`cleanName`: no control, format, bidi or blank-drawing characters, no stacked marks) and compared for the duplicate-name marker after NFKC folding and mapping common Cyrillic/Greek look-alikes (`nameKey`). The marker is shown as text on the PC's tab ("same name · #xxxx"), with a tag from the first 4 characters of the deviceId this browser chose for that PC, which the PC can't pick.
  - Misbehaving PCs: more than 50 unsolicited frames in 10 s (previews for instances not asked for once the PC confirmed the targets, frames that don't decrypt, malformed events) end that PC's session in the dashboard. A refused or lost `subscribePreviews` is retried with backoff (5 tries), and frames for the old targets aren't struck until 2 s after the PC confirmed or the last try failed; asking again before the PC confirmed keeps the first ask's time, so a PC that never confirms gets at most that first ask's retries plus 2 s (about 57 s) for the old targets, however often it makes the dashboard ask again (`unsubscribe`, "kept sending data this dashboard did not ask for"). Each PC has its own seal chain and inbound queue, so one PC never delays another.
  - Previews: `RemoteSettings.allowViewPreviews` (default on). When off, a View device's `subscribePreviews` gets `rpcResult` code `previews_off`, and the dashboard stops asking until the next `pc_online`. Preview frames for instances outside the last `setPreviewTargets` set are dropped. Those for an instance that was asked for before count as strikes only once the PC confirmed the change, or all 5 tries of it failed, and 2 s have passed; all others always do. Per stream the PC keeps at most 3 pictures unacknowledged; one not acknowledged within twice the measured ack time (1 s to 8 s) counts as lost, and each loss halves that window and the stream's rate (down to 1/16), each ack wins a step back, so a slow link gets fewer, fresher pictures instead of a full relay queue. The dashboard acks each picture at once while its budget of 90 acks a second per PC lasts (the PC never sends a viewer more pictures than that), and otherwise once a token frees up, for the newest picture; a coarser ack (one per 100 ms) would cap a 30 FPS stream with a 3-frame window at 3 / (100 ms + RTT). Capture and encode run off the session loop, one batch in flight; within a batch each (client, width, quality) is captured and encoded once and handed to every viewer asking for it; all viewers together share a budget of 120 pictures per second (`PC_FPS_BUDGET`) on top of the 90 per viewer.
  - Input (`instances/remote_input.rs`): only Control devices, only while Windows is unlocked, only onto the client area, and every touch / camera Down must hit the client window (`WindowFromPoint`). Every held key, finger and drag belongs to the session that started it: only that session moves or releases it, and `release_owner(viewerId)` lets go of just its input and drops its queued events (session drop, role change); `release_all()` (Windows lock, relay connection end, pause) lets go of everyone's. `release_all()` is never triggered by a viewer, so one device can never let go of another's input. Release events (`inputKey down:false`, `inputTouch` / `inputCamera what:"up"`) use the lift budget; from a View device they do nothing. While Windows is locked the input worker lets go of everything and drops every queued event except lifts, including input queued before the lock. A release never moves: the dashboard sends the drag's last stretch as `inputCamera what:"move"` before `what:"up"`. The dashboard re-sends `inputKey down:true, repeat:true` for held keys and `inputCamera what:"move"` at the last position every 250 ms; a `repeat` for a key the PC already let go is ignored (only a fresh press brings the client forward again). The PC lets go of any key, right button or touch contact not refreshed for 750 ms, and when the client loses the foreground. The input queue is bounded (64), at most 16 presses and 16 lifts per device across all of its sessions (a press over that gets `busy`; a lift over it lets go of everything that session holds), and a device holds at most 5 of the 10 touch contacts. A press checks again, right before it is sent, that Windows isn't locked and that the pid still has the start time it was checked with. A hung client is never brought forward. If the input thread is stuck on one event for 750 ms (while it restores a minimized client: for that restore's longest designed wait, `window::UNHIDE_TIME`, plus 1 s), a deadman thread lets go of every key and the right button and drops everyone's held and queued input. Lifts are queued even when the tracker no longer has the client's window. A camera drag presses the right button only with the cursor on the client's area and the client in front, and lets go when a move finds the client no longer in front or the cursor no longer on it before moving (moves are relative, so where a move leaves the cursor doesn't matter). `release_now` (exit) also stops all later presses, and sends the key-ups itself if the input thread doesn't answer in time. Anti-AFK leaves the focus alone while a phone holds anything. The dashboard lets go of held keys and drags when the live picture goes away.
  - Pause: the title-bar pill (or the tray's "Stop remote watching" while a device watches) calls `remote_set_paused(true)`, stored as the DB setting `remote_paused`. Pausing closes an open pairing (its joiner gets `{mode:"closed"}`) and drops every session with `kick_viewer` code `paused`, so each dashboard says the PC paused Remote instead of calling it offline; while paused Remote stays off the relay; `pc_hello` / `pc_tokens` send no tokens. `RemoteStatus` has `watching` (viewers with preview subscriptions) and `paused`.
  - Reconnects: the PC and the dashboard both use full-jitter backoff (0.5 s + random up to min(60 s, 2 s * 2^n)). Only a connection that stayed up for 30 s resets it, and then to a cap of about 8-10 s, so a relay that accepts and drops sockets doesn't get a fast retry loop. The PC's connect has a 15 s timeout and it reconnects after 60 s of relay silence. The dashboard opens no socket while the tab is hidden and resubscribes when it becomes visible again.
- **Pairing (v2, `crypto.rs` ↔ `crypto.ts`, shared vectors in both test suites):**
  - **Goal:** the relay only routes `pair_open` / `pair_close` / `pair_join` / `pair_msg` / `pair_joined` and never inspects their `data`. The browser's identity (`deviceId`, `devicePub`, `label`) only ever travels sealed under the pair key, and every pairing needs an explicit **Approve** on the PC.
  - **Per-PC browser identity:** for each pairing the browser makes a fresh random `deviceId` (UUID) and a non-extractable ECDSA P-256 key, stored with that PC's record in IndexedDB and used only for that PC's subscribe and session handshake, so two PCs can't link one browser by its id. The relay still can: one socket's `subscribe` lists every PC on that relay together, and it sees the browser's IP and timing.
  - **Framing:** every `pair_join.data` / `pair_msg.data` is `base64url(JSON)` with a `mode` field. Every browser `pair_join` carries `"proto": 2`. The manual flow sends its second `pair_join` with the `pairId` the PC revealed (the relay keeps routing the same viewer socket into the same room).
  - **Transcript:** `th = SHA-256("roalt-remote-v2-pair" || mode || len(pairId): u8 || pairId || pcEphem(65) || browserEphem(65) || nonce(32))`, mode `0x01` = QR (both ephemerals empty), `0x02` = manual. `nonce` is 32 random bytes chosen by the browser.
  - **Sealed blobs:** `base64url(iv(12) || AES-256-GCM(ct || tag))` with AAD = `"roalt-remote-v2-blob" || dir || pairId`, `dir` = `0x02` browser→PC, `0x01` PC→browser, so a blob can never be reflected back as the other direction.
  - **Device binding (browser → PC, sealed):** `{deviceId, devicePubB64, label, sigB64}`, `sig = ECDSA_device("roalt-remote-v2-device" || th || deviceId(16) || devicePub(65))`. The PC enrolls only these decrypted, signature-checked values.
  - **Ack (PC → browser, sealed):** `{mode:"ack", blob}` with `{pcId, pcName, pcPubB64, roomToken, role, sigB64}`, `sig = ECDSA_pc("roalt-remote-v2-pc" || th || pcId(16) || pcPub(65) || deviceId(16))`. The browser accepts the ack only if pcId is a lowercase UUID, roomToken is 43 base64url chars, pcName (cleaned) is 1–64 code points, the signature verifies for its own transcript and deviceId, and no stored PC has the same pcId with a different pcPub. `role` other than `"control"` is read as `"readonly"`. In manual mode the signature is self-certified (pcPub comes in the same ack), so only the SAS authenticates the PC there.
  - **Confirm, then enroll:** a verified ack is only an offer. The browser stores nothing until the user confirms on it: "Pair with <pcName>?" for QR, and for a manual code the SAS shown again with "Codes match, pair" (pair only if RoALT showed the same code and you clicked Approve there). Before that the browser checks that no stored PC has the same pcId with a different pcPub (else it gives up). Then it sends `{mode:"done", blob: seal(pairKey, {mode:"done", replaces?})}` in a `pair_join` on the same socket. Approve gives this step its own time: the PC's pairing then lasts until at least 60 s after the Approve (`PAIR_CONFIRM_MS`) and it tells the relay (`pair_extend`), the browser's own timeout moves to at least 60 s after the ack, and the PC dialog shows the time left instead of cancelling while it waits for the device. The blob is required and its sealed `mode` must be `"done"` (so no other browser→PC blob, such as the device binding, can stand in for it); a missing or invalid one aborts the pairing. The PC writes the device row only now, as **pending** (`remote_devices.pending_ms`, migrations 022 and 023; listed as "Waiting for its first connection"), sends `pc_tokens`, answers `{mode:"enrolled", blob: seal(pairKey, PC→browser, {"mode":"enrolled"})}` and closes the room. The browser saves the PC only on an `enrolled` whose blob opens under its pair key with sealed `mode` `"enrolled"` (`isEnrolledBlob`; shared vector `INTEROP_ENROLLED_BLOB` in `mod.rs` and `crypto.test.ts`); any other `enrolled` fails the pairing, so the relay can't make the browser overwrite a working record. The device's first session that decrypts (`remote_device_touch_seen`) confirms the row and shows the "paired" toast; a pending row that gets none within 10 minutes of connected, unpaused time is deleted with an "expired" toast. The row keeps the time it has left: each 3 s tick of a relay connection takes off the time since the last tick, at most 6 s, so time offline, paused or asleep never counts and a new connection brings no time back, so a lost `enrolled`, a failed save or a closed tab leaves nothing behind. Pairing is refused while Remote is paused (checked again when the pairing is installed, so a Pause at the same moment can't leave one open). A browser re-pairing a PC it already has keeps both devices: the new one, and the one it replaced as `previous`. It refuses another re-pairing of that PC until one of the two has had a session (and says so before anything is enrolled), so it never holds a third device the PC may be the only one to know. Until one of the two has had a session it switches between them every 15 minutes and never drops either (the newest is tried first for at least a minute after the dashboard opens); then it keeps that one and drops the other. Every change to the stored PCs is one IndexedDB readwrite transaction, so tabs can't undo each other's changes (a Forget included), and a storage failure shows an error screen with "Try again". There is no cancel message: a browser that gives up (Cancel, "Pair with…?" declined, a bad ack, a key clash) closes its socket, the relay sends `pair_left`, nothing is enrolled and the PC says the device left; the same happens when the pairing expires. Any other `mode` from the joiner (an old `{mode:"cancel"}` included) is an invalid message and aborts the pairing visibly. `replaces = [{deviceId, sigB64}, …]` is sent when this browser already holds a record for the same pcId and pcPub, one entry for each device it holds there (the current one, and its `previous` if a re-pairing is still unconfirmed): each `sig` is that device key's binding signature over this pairing's `th` (its deviceId, its devicePub); the PC verifies each with the stored key at `done` and deletes every row it proved when the new device confirms (then sends `pc_tokens`, which also ends any session of the old device), so a pairing that never completes doesn't break the old one.
  - **QR:** URL `https://remote.roalt.dev/#pair=<pairId>.<32B secret base64url>` (`#fragment` never sent to a server; scrubbed via `history.replaceState`), the same for every relay (the dashboard ignores anything after the secret). `qrKey = HKDF-SHA256(secret, salt=pairId, info="roalt-remote-v2-pair-qr")`. Browser → `{mode:"qr", nonceB64, blob: seal(qrKey, binding)}`. The PC shows the request (label, no SAS) and waits for Approve. A browser that opened a QR link accepts only an ack sealed under `qrKey` and ignores any manual-flow message; it tells the user that RoALT must show the request as "Scanned the QR code" with no 6-digit code, and to Deny otherwise. Whoever saw the manual code (the relay included) can still send a manual request into the same pairing, so the PC dialog always labels a request "Scanned the QR code" or "Typed the pairing code", and for a typed one shows the SAS with "If you scanned the QR code, click Deny".
  - **Manual 8-char code (`ABCD-1234`), commit-then-reveal:**
    1. Browser → `{mode:"manual_commit", commitB64}`, `commit = SHA-256("roalt-remote-v2-commit" || browserEphem(65) || nonce(32))`.
    2. PC → `{mode:"manual_challenge", pairId, pcEphemPubB64}` (fresh PC ephemeral, made only after the commitment).
    3. Browser → `{mode:"manual_reveal", ephemPubB64, nonceB64, blob: seal(pairKey, binding)}`. The PC checks the commitment, then derives from `ECDH(ephemerals)` with `salt = th`: `pairKey = HKDF(info="roalt-remote-v2-manual")` (32 B) and the SAS `= u32 BE(HKDF(info="roalt-remote-v2-sas", 4 B)) % 1_000_000` shown as `"123 456"` on both screens. A man in the middle must fix its keys before it sees the other side's, so it gets one 1-in-a-million guess per pairing.
  - **PC rules:** the pairing locks onto the first joining viewer; a second viewer, an out-of-order message or any failed check aborts it (`{mode:"aborted"}`, `pair_close`, desktop warning), also after approval. Both ends word an abort neutrally ("another device used the code, or the request was changed on the way"; the PC adds "or the connection to the relay dropped"). The relay forgets a room and its joiner with the PC's connection, so when that connection ends a pairing someone already joined is aborted (nothing approvable is left behind, and pair messages that were queued for the old connection don't matter); one nobody joined is opened again (`pair_open`) on the next connection. An expired pairing is hidden from `remote_status` but only removed by the connection's sweep, which sends `pair_close` and goes idle when nothing is paired. `remote_pair_approve(viewerId, approve, role, sas)` must pass back the SAS the user saw (`null` for QR) or it is refused; Approve stays disabled for 1 s after a request appears. The role picker and the command default to View only; every pairing ends with a toast (`remote://pairing` `{outcome:"paired", label}` on the device's first session, `{outcome:"expired", label}` when it never came, or `{outcome:"left"}`). With 64 devices paired, starting or approving a pairing is refused. Deny sends `{mode:"denied"}`. On `{"t":"err","code":"pair_taken","pairId"}` the PC makes a fresh pairId, manual code and QR secret and sends `pair_open` again (the dialog shows the new code), at most 5 times per pairing and only before anyone joined; otherwise the pairing is aborted. While the PC is not connected to the relay the dialog hides the code and QR (the relay holds no room for it then). After Approve the PC keeps showing the SAS, and in manual mode the browser's last step reads "Compare with your PC", not "Approved": the ack is self-certified there. Starting a new pairing closes the previous one (`pair_close`, and `{mode:"denied"}` to its joiner); cancelling sends `{mode:"closed"}` and expiry `{mode:"expired"}` to the joiner, also for a message that reaches an expired pairing; an aborted pairing no longer keeps the relay connection up; the 64-device check comes before Remote is switched on. Device labels are cleaned before display (no control (Cc), format (Cf, every bidi control included), line/paragraph separator, filler or tag characters, at most one mark (any Mn/Mc/Me) per character), and the approval card clips them to two lines. The dashboard warns on the "Pair with…?" screen when the PC's name looks like one it already has.
